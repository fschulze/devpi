==========================================================
Documentation writing guide
==========================================================

* Default to female if you must use a person as an example.
    There are enough male tech users.
* Use they/them where it makes sense
    You cannot assume the gender of a user, or even if a user is a single person. they/them covers any eventuality.
    Exceptions are made where referring to a specific individual, where you should use their chosen pronouns if known.
* Use plain language
    An example of the benefits of consistent language: https://catalyst.harvard.edu/writing-communication-center/write-effectively/plain-language/
* Ensure consistent use of terms
    If something does not have a defined term, then update :doc:`glossary` with an explanation
* Use private / local for Indexes
    Previous documentation may use different terms. If you come across this, update it.
* Write only what you know.
    Feel free to ask for details when uncertain.
* Abbreviations only when declared just before or very common and expected like HTML.
    Hard to look up abbreviations like a11y or i18n are forbidden
* Write whole words instead of contractions.
    For example: use "have not" or "it is" instead of "haven't" or "it's".
* Avoid negations.
    Use language such as "x is forbidden" rather than "do not do x".
* Use modern terminology for allow/blocklists and primary/replica systems.
    Terms like whitelist/blacklist and master/slave are considered outdated.
* Keep documentation current.
    *If something needs updating, update it.*
* Adhere to the :doc:`code-of-conduct`
* Keep examples accessible
    * Ensure document design adheres to accessibility guidelines.
    * Examples and writing should being accessible to those with less knowledge of the system and even english language.
    * A base level of english can be assumed, but use plain language wherever possible.
